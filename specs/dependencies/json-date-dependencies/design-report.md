# JSON/날짜 의존성 공급 설계

설계 준비 결과와 미실행 표시는 설계 단계 당시의 기록이다.
최종 구현/검증 결과와 현재 후속 상태는 [QA](qa-report.md)에서 확인한다.

## 단계 결과

### 설계 범위와 산출물 목록

두 라이브러리의 소스 공급과 독립 소비 검증을 한 플로우로 수행한다.
이 report에 공급 구성, 소비 인터페이스, 원본 관리와 검증/QA의 판정 기준을 정의한다.
구현용 상세를 별도 파일로 분리하거나 순차 번들을 만들 필요는 없다.

### 작업 모델과 승인

[논의의 작업 모델과 승인](discussion-report.md#작업-모델과-승인)을 재사용한다.
모델, 강도와 담당 범위를 변경하지 않는다.
교차 검토 모델은 아직 승인받지 않았다.

### 복귀 및 재검토 기록

최초 설계이며 복귀 및 선행 report 변경은 해당 없음.

- 회귀 계기가 된 report: 해당 없음.

### 설계 기준과 입력

#### 입력 자료

[논의](discussion-report.md)의 요구사항, 명칭과 승인 근거를 입력으로 사용했다.
변경한 작업명, 여섯 체크 항목의 근거와 설계 인계를 실제 내용에 대조하고 정형 검사를 통과했다.

#### 설계 대상

논의의 F1-F5와 Q1-Q4를 구현 및 검증 가능한 공급 계약으로 구체화한다.
요구사항의 정본과 제품 구현 경계는 논의를 따른다.

#### 스펙의 단위와 선택 근거

계약 중심으로 JSON/날짜 의존성의 오프라인 소비 가능성을 하나의 공급 단위로 정한다.
두 라이브러리는 같은 소스 관리, Cargo 연결과 반환 자료를 사용한다.
필요한 원본 준비와 검증 환경을 함께 확인할 수 있어 별도 번들 분할을 하지 않는다.

#### 적용할 제약

Rust/Cargo 1.89.0, 기존 serde 1.0.229와 기존 공급 경로를 유지한다.
새 패키지는 crates.io 배포 소스로 공급하며 새로운 Git 저장소 스냅샷은 추가하지 않는다.
전역 Cargo 설정과 타 프로젝트 제품 코드는 변경하지 않는다.

#### 넘겨받은 미결정 사항

정확한 버전/기능과 전이 소스, 검증 구성, 회귀 범위 및 환경 준비를
아래 공급 구성, 테스트 계획과 환경 근거에서 구체화했다.

레지스트리 패키지 수는 현재 171개에서 176개가 된다.

#### 의존 관계와 고정 구성

| 패키지 | 버전 | 선언 또는 활성 기능 | 최소 Rust 버전 | 처리 |
| --- | --- | --- | --- | --- |
| serde_json | 1.0.151 | default-features=false, std | 1.71 | 신규 공급 |
| chrono | 0.4.45 | default-features=false, std. 활성 기능은 alloc, std | 1.62.0 | 신규 공급 |
| zmij | 1.0.23 | 추가 기능 없음 | 1.71 | 신규 전이 소스 |
| num-traits | 0.2.19 | default-features=false, 활성 기능 없음 | 1.60 | 신규 전이 소스 |
| autocfg | 1.5.1 | 활성 기능 없음 | 1.0 | 신규 빌드 소스 |
| serde / serde_core | 1.0.229 | 검증용 serde는 std, derive. 실제 전이 기능은 metadata로 기록 | 1.56 | 기존 원본 재사용 |
| itoa | 1.0.18 | 활성 기능 없음 | 1.68 | 기존 원본 재사용 |
| memchr | 2.8.3 | alloc, std | 1.61 | 기존 원본 재사용 |

검증용 derive에는 기존 serde_derive 1.0.229, proc-macro2 1.0.107, quote 1.0.47,
syn 3.0.6과 unicode-ident 1.0.26을 사용한다.
이 패키지도 기존 원본을 재사용하며 새 버전으로 교체하지 않는다.

chrono의 clock, now, wasmbind, serde와 로컬 시간대 관련 기능을 활성화하지 않는다.
serde_json의 preserve_order, arbitrary_precision 및 기타 선택 기능도 활성화하지 않는다.
최종 잠금 파일과 활성 기능에서 이 조건을 검증한다.

#### 공개 인터페이스

소비자는 자신의 Cargo.toml에서 다음과 같이 선언하고 자신의 Cargo.lock을 관리한다.

```toml
serde_json = { version = "=1.0.151", default-features = false, features = ["std"] }
chrono = { version = "=0.4.45", default-features = false, features = ["std"] }
```

검증 구성은 기존 serde 1.0.229의 std/derive를 직접 선언하여 typed JSON 해석과 직렬화의 호환성을 확인한다.
소비자 전체가 derive를 반드시 활성화해야 한다는 계약은 아니다.

| 진입점 | 입력과 결과 | 오류 및 부수 효과 |
| --- | --- | --- |
| `python3 scripts/flax.py cargo-db <Cargo 인자>` | Cargo 인자를 기존 방식으로 전달. 새 검증은 `test --manifest-path checks/json-date-smoke/Cargo.toml --locked --offline` | build 아래 설정/캐시/레지스트리 뷰/빌드 결과 생성. 원본 누락 또는 Cargo 실패는 기존 종료 코드로 전달 |
| `serde_json::from_slice<T>(&[u8])` | 원본 JSON 바이트를 Value 또는 Deserialize 타입으로 해석 | 잘못된 JSON/타입은 serde_json 오류. 원본 바이트를 변경하지 않음 |
| `serde_json::to_vec/to_string/to_writer` | Serialize 타입을 JSON 바이트/문자열/출력 대상으로 직렬화 | 직렬화/출력 실패를 오류로 전달. JSONL은 JSON 레코드 사이에 LF를 추가 |
| `NaiveDate::parse_from_str(text, format)` | `%Y%m%d` 또는 `%Y-%m-%d`의 실제 달력 날짜 | 유효하지 않은 달력 날짜는 ParseError |
| `DateTime::parse_from_rfc3339(text)` 및 `timestamp_micros()` | 명시적 offset 시각을 해석하고 i64 UTC microseconds를 얻음 | 잘못된 RFC3339 시각은 ParseError. 현재 시간 및 로컬 시간대 조회 없음 |
| `str::parse::<u64>()` | JSON 문자열 필드의 비음수 정수를 정확하게 해석 | 범위 초과/잘못된 정수 문자열은 ParseIntError. 부동소수점 경유 없음 |

새 제품 API, DB 스키마나 파서 오류 정책을 정의하지 않는다.
검증 내부의 fixture 타입과 보조 함수는 위 계약 범위에서 구현 단계에 작성한다.

#### 저장소와 모듈 경계

새 원본, 검증 구성과 안내는 Flax가 소유한다.
검증은 외부 소스를 실제로 연결하는 Flax의 독립 소비 crate에 둔다.
Walnut의 전체 입력/저장 흐름과 Rosemary/Walnut의 서브모듈 갱신은 해당 프로젝트 책임이다.

### 동작과 데이터 흐름

#### 주요 처리 흐름

1. 준비한 고정 .crate 아카이브의 SHA-256을 crates.io 체크섬과 대조한다.
2. 신규 5개 패키지만 분류 경로에 반입한다. 아카이브 파일 전체와 라이선스 및 .cargo_vcs_info.json을 보존한다.
3. 각 패키지의 파일별 SHA-256과 배포 체크섬으로 .cargo-checksum.json을 작성하고 레지스트리 메타데이터를 추가한다.
4. 독립 소비 구성의 잠금 파일을 Flax 디렉토리 소스로 오프라인 생성한다.
5. 깨끗한 별도 캐시와 빌드 경로에서 잠금 파일을 고정한 소비 테스트를 실행한다.
6. 실제 활성 기능과 원본 무결성 및 기존 소비 회귀 결과를 기록하고 안내를 갱신한다.

#### 데이터 흐름

| 입력 | 변환 | 기대 결과 |
| --- | --- | --- |
| crates.io 배포 체크섬과 .crate | SHA-256 대조, 파일 목록/체크섬 보존 | 검증 가능한 원본과 rust-registry.json 항목 |
| 검증용 JSON 응답 바이트 | serde_json 해석, 날짜/정수 문자열 변환 | 날짜와 u64 값. 원본 바이트는 별도 보존 |
| 검증용 manifest의 samples[].retrieved_at | RFC3339 해석, UTC microseconds 변환 | offset 표현과 Z 표현에 같은 i64 값 |
| 해석한 값 및 검증 결과 레코드 | JSON 직렬화, LF로 JSONL 레코드 구분 | 재해석 가능한 JSON/JSONL, u64 정밀도 보존 |
| Cargo metadata | resolve node의 package/version/features 수집 | `features-linux.json`에 실제 활성 기능 기록 |

manifest 검증 fixture의 실제 필드명은 Walnut의 `samples[].retrieved_at`을 사용한다.
응답 검증 fixture는 현재 `daily-raw-01.json` 첫 행에서 필요한 공개 필드를 추출하여 독립 입력으로 보관한다.
테스트 실행 때 Walnut 파일이 없어도 실행되며, 전체 원본 6개/482행을 복사하거나 재검증하지 않는다.

#### 상태 변화

준비 아카이브와 설계용 소비 구성은 `build/json-date-preparation/`에 있다.
설계 승인 전에는 third_party에 반입하지 않는다.
구현 후에는 레지스트리 목록과 새 원본이 일치해야 하며, 검증 통과와 단계 승인 상태를 구분한다.

#### 오류 및 예외 흐름

체크섬 불일치, 원본 경로 충돌이나 미공급 의존성이 있으면 해당 작업을 실패로 기록한다.
기존 소스를 덮어쓰거나 온라인 소비로 바꾸어 실패를 감추지 않는다.
고정 버전/기능/도구 체인 변경이 필요하면 근거를 제출하고 선행 설계를 변경한 뒤 진행한다.
기존 네트워크 회귀 검사는 샌드박스 밖의 localhost 권한이 필요하다.
실행 권한을 확보하지 못한 경우 미실행으로 기록하며 통과로 판정하지 않는다.

### 선택한 설계와 판단 근거

#### 주요 설계 결정과 선택 이유

배포 패키지를 기존 디렉토리 소스에 추가하는 방식으로 공급한다.
기존 Cargo CLI와 패치 목록을 수정할 필요 없이 새 패키지를 소비할 수 있다.
요청 기능만 포함한 두 패키지를 독립 소비 crate에서 함께 검증한다.

원본 Cargo.toml과 crates.io 메타데이터의 MSRV를 확인했고,
Rust/Cargo 1.89.0의 임시 오프라인 소비 프로그램에서 기존 serde/전이 소스와 실제 빌드 및 실행을 확인했다.
공급할 두 라이브러리와 신규 전이 소스 3개의 정확한 버전은 위 고정 구성 표를 따른다.

#### 검토한 대안과 선택의 영향

chrono 기본 기능은 clock, std, oldtime과 wasmbind를 포함한다.
요청에 필요하지 않은 시간대/플랫폼 의존성을 줄이기 위해 기본 기능을 끄고 std만 선언한다.
serde_json도 std만 선언하여 순서 보존이나 임의 정밀도 기능을 추가하지 않는다.
정수 문자열의 정확한 u64 변환은 Rust 표준 파서를 사용한다.

새 Cargo 모드를 추가하는 대신 기존 protoc 없는 cargo-db 경로를 사용한다.
명령 이름에 DB가 포함되어 있지만 실행 계약은 protoc 없는 일반 Cargo 소비이므로 이번 요구를 만족한다.

#### 넘겨받은 미결정 사항의 처리

버전/기능과 전이 목록은 준비한 원본 및 실제 Cargo 그래프로 확인했다.
구현 경로, 입력 자료와 판정 기준 및 회귀/QA 범위는 이 report에 정의했다.
구현을 막는 추가 설계 질문은 없다.
설계용 소비 실행은 최종 검증 테스트 전체를 통과했다는 의미가 아니다.

### 테스트 계획

#### 외부 의존성 격리 방법

다운로드는 소스 준비에만 사용하며 최종 소비 검사는 빈 CARGO_HOME과 별도 빌드 경로에서 오프라인 수행한다.
새 소비 검증은 외부 서버나 네트워크를 사용하지 않는다.
기존 DB 회귀는 기존 run.py가 임시 PostgreSQL 클러스터/계정/인증서를 준비하고 검사 후 정리한다.
기존 gRPC 회귀는 localhost의 검증 서버를 사용한다.

#### 통합 테스트 적용 여부와 범위

Flax가 소스 연결을 책임지므로 `checks/json-date-smoke/`에 독립 소비 통합 검증을 둔다.
실제 serde, serde_json 및 chrono를 연결해 입력 변환과 JSON/JSONL 결과를 확인한다.
원본 패키지의 자체 테스트나 라이브러리 구현을 변경하지 않는다.

#### E2E 테스트 적용 여부와 범위

Flax는 외부 의존성 공급 저장소이며 최상위 제품 플랫폼이 아니므로 제품 E2E는 적용하지 않는다.
Walnut의 전체 482행 파싱/저장/조회와 DB QA는 승인된 논의에서 해당 프로젝트 책임으로 구분되어 있다.

#### 검증용 항목과 판정 기준

## 인계 사항

### 단계와 인계 대상

구현 진입은 이 설계의 사용자 최종 승인 후 수행한다.

### 구현 시 참조할 자료

이 report의 구성 요소/고정 구성/소비 인터페이스, 처리 흐름과 V1-V9가 구현 및 테스트 기준이다.
원본 무결성 검사는 [verify-sources.py](../../../scripts/verify-sources.py),
소비 연결은 [flax.py](../../../scripts/flax.py)의 기존 구현을 사용한다.

### 구현용 모델과 추론 강도

[논의의 모델 승인](discussion-report.md#작업-모델과-승인)을 적용한다.
같은 모델과 강도 및 승인 범위이므로 추가 전환 확인은 없다.

### 작성 단계에서 확인할 사항

준비한 아카이브와 최종 반입 파일의 동일성, 기존 원본 재사용 및 빈 캐시 소비를 실제 구현에서 확인한다.
features-linux.json은 최종 소비 구성에서 다시 수집한다.
설계 준비용 임시 소비의 성공을 최종 V1-V9 통과로 옮기지 않는다.

### 이번 작업에서 제외하거나 미룬 설계 사항

논의의 제외 범위를 유지한다.
별도 설계 보류나 새 후속 번들은 없다.

### 구현 순서와 주의사항

소비 선언/fixture/검증을 먼저 작성하여 미공급 상태의 실패를 확인하고,
원본 반입과 레지스트리 갱신 후 실제 오프라인 소비 성공을 확인한다.
기존 원본이나 Cargo.lock을 새 버전으로 교체하지 않는다.
새 검증 Cargo.lock만 생성하고 lockfiles에 연결한다.
원본 무결성과 기존 회귀를 확인한 뒤 소비 문서와 실제 결과를 대조한다.
