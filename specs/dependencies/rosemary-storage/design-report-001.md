# Rosemary 저장 의존성 공급 설계

이 문서는 구현에 적용한 구조, 인터페이스와 판정 기준을 기록한다.
환경 준비 결과는 설계 당시의 사전 확인이며 최종 실행 결과는
[검증](verification-report-001.md), 현재 반환 상태는 [최종 QA](qa-report-001.md)를 따른다.

## 단계 결과

### 작업 모델과 승인

[논의 기록의 작업 모델과 승인](discussion-report-001.md#작업-모델과-승인)을 재사용한다.
설계 단계의 별도 모델 또는 에이전트 실행은 없었다.

### 복귀 및 재검토 기록

최초 설계이며 해당 없음.

- 회귀 계기가 된 report: 해당 없음.

### 설계 기준과 입력

#### 입력 자료

[승인된 논의](discussion-report-001.md)의 확정 요구사항을 적용한다.
원래 PostgreSQL 및 parking_lot 요청은 Git에서 제외되는 로컬 data/todo 자료이며,
소비 계약과 검증 완료 조건은 논의 기록에 보존한다.

#### 설계 대상

두 요청서의 고정 버전과 기능을 유지한 소스 공급, DB 전용 오프라인 소비,
기존 gRPC 회귀와 실제 PostgreSQL 및 기본 잠금 검증을 다룬다.
요구사항의 정본은 [논의의 범위와 요구사항](discussion-report-001.md#범위와-요구사항)이며 이 설계에서 변경하지 않는다.

#### 스펙의 단위와 선택 근거

소비 계약을 기준으로 다음 세 책임을 구분한다.

1. 소스 공급: 잠금 파일에 필요한 원본 패키지와 출처, 체크섬 및 라이선스를 제공한다.
2. Cargo 연결: 소비자의 선언과 잠금 파일로 Flax 소스를 오프라인에서 사용한다.
3. 소비 검증: DB, TLS와 잠금의 기본 사용 가능성을 실제 실행 근거로 확인한다.

같은 소스 및 소비 경로를 공유하므로 한 작업에서 구현과 검증을 수행한다.
Rosemary의 제품 구현과 정확성 판단은 포함하지 않는다.

#### 적용할 제약

[논의의 범위와 요구사항](discussion-report-001.md#범위와-요구사항) 및
[지켜야 할 제약](discussion-report-001.md#지켜야-할-제약)을 적용한다.
새 직접 버전, 암호 제공자나 전역 설정을 선택하지 않는다.
기존 소스와 gRPC 잠금 파일을 보존하고, DB 실행 결과를 환경 준비 결과와 구분한다.

#### 넘겨받은 미결정 사항

아래 항목은 이 설계에서 확정했으며 미처리 상태가 아니다.

Cargo 인터페이스, 소스 배치 및 버전 공존, 서버와 인증서의 격리,
검증 조건과 실제 검사 구성을 이 설계의 아래 항목에서 결정한다.

### 구조와 책임

#### 구성 요소와 책임

| 구성 요소 | 책임 |
| --- | --- |
| third_party의 기존 분류 디렉토리 | 추가 crate의 원본 소스, 고지문과 Cargo 체크섬 보존 |
| third_party/rust-registry.json | 기존 및 신규 레지스트리 패키지의 버전, 경로와 출처 기록 |
| scripts/flax.py | 공용 벤더링 연결 생성과 gRPC 또는 DB용 Cargo 실행 |
| checks/cargo의 Python 검사 | protoc 없는 DB 설정과 기존 Cargo 명령의 계약 검증 |
| checks/postgres-smoke의 Rust 구성 | 요청 패키지의 실제 사용과 DB 동작 검증 |
| checks/postgres-smoke의 실행기 | 전용 서버, 인증서, 계정 및 실행 자료 준비와 정리 |
| docs/rosemary-integration.md | 소비 연결, 환경 설치, 재현 명령과 공급 결과 안내 |

[원본 소스 검사](../../../scripts/verify-sources.py)는 기존 방식으로 전체 원본을 검사한다.

#### 의존 관계

소비 프로젝트와 Flax 검증 구성은 scripts/flax.py를 통해
로컬 patch와 레지스트리 소스 대체를 적용한다.
DB 실행기는 별도 PostgreSQL 서버를 준비하고 Rust 검증에 접속 정보를 전달한다.
Rosemary 저장 코드와 Flax 검증 코드 사이에는 실행 의존성을 추가하지 않는다.

#### 공개 인터페이스

기존 명령과 build-dir 옵션을 유지한다.

```sh
python3 scripts/flax.py cargo <Cargo 인자>
python3 scripts/flax.py --build-dir <출력 경로> cargo <Cargo 인자>
```

DB 및 protoc 없는 일반 Rust 소비에는 새 명령을 제공한다.

```sh
python3 scripts/flax.py cargo-db <Cargo 인자>
python3 scripts/flax.py --build-dir <출력 경로> cargo-db <Cargo 인자>
```

두 명령은 Cargo의 인자를 같은 방식으로 그대로 전달한다.
cargo는 기존대로 protoc를 검사하고 PROTOC 및 PROTOC_INCLUDE를 설정한다.
cargo-db는 protoc 파일을 요구하지 않고 이 두 변수의 Flax 강제 설정을 생성하지 않는다.
공통 patch, 레지스트리 연결, offline 설정과 build 아래의 전용 Cargo 캐시 및 target을 사용한다.
각 모드의 설정 파일은 `cargo-config.toml`과 `cargo-db-config.toml`로 구분한다.

검증 실행기의 인터페이스는 다음과 같다.

```sh
python3 -B checks/postgres-smoke/run.py
python3 -B checks/postgres-smoke/run.py --build-dir <출력 경로> --pg-bin <PostgreSQL 16 바이너리 경로>
```

성공한 검사는 이름과 결과를 출력하고, 실패 또는 환경 미준비는 비정상 종료한다.
DB를 실행하지 못했을 때 검사를 자동으로 생략하여 전체 성공으로 표시하지 않는다.
로그는 지정한 출력 경로 아래에서 실행별로 분리하고 경로를 반환한다.

#### 저장소와 모듈 경계

Flax가 검증 구성의 Cargo.toml과 Cargo.lock을 소유한다.
소비 프로젝트는 자신의 선언과 잠금 파일을 소유하며 물리적인 crate 경로를 선언하지 않는다.
라이브러리 소스는 Flax에서만 관리한다.
사용자 전역 설정, Rosemary 코드와 시스템 기본 PostgreSQL 클러스터 설정은 변경 대상이 아니다.

### 동작과 데이터 흐름

#### 주요 처리 흐름

소스 공급은 준비한 잠금 파일, 메타데이터와 vendor 결과를 입력으로 한다.
기존과 동일한 이름 및 버전은 체크섬을 대조하여 재사용하고,
새 이름 또는 필요한 다른 계열만 원본 그대로 반입한다.
목록과 경로를 갱신한 뒤 전체 소스 무결성을 검사한다.

Cargo 연결은 레지스트리 목록을 읽어 기존의 평면 디렉토리 소스 뷰를 만든다.
이미 존재하는 일반 파일은 교체하지 않는 기존 경계를 유지한다.
선택한 모드의 설정을 생성하고 소비자의 Cargo 명령을 실행한다.

DB 실행기는 새 작업 디렉토리와 사용 가능한 루프백 포트를 준비하고,
정상 TLS, 만료된 인증서의 TLS, TLS OFF 전용 클러스터를 각각 기동한다.
검증 DB와 제한된 계정을 준비한 뒤 Cargo 검사를 실행한다.
성공과 실패 모두 서버를 종료하고 인증 정보 및 개인 키가 포함된 작업 디렉토리를 정리한다.

#### 데이터 흐름

레지스트리 목록의 기존 패키지 필드를 유지하고 검증용 잠금 파일들의 목록을 추가한다.
기존 `lockfile` 필드는 gRPC 경로를 유지하며,
새 `lockfiles` 필드는 gRPC와 PostgreSQL 검증 구성의 잠금 파일을 연결한다.
각 추가 패키지는 이름, 버전, 경로, registry, repository, 가능한 원본 commit,
package_sha256, license, license_file과 classification_basis를 기록한다.

Rust 검증과 실행기 사이의 계약은 다음 환경 입력으로 한다.
검증 시작 때 필수 입력의 존재를 검사하고 누락되면 실패한다.

| 입력 | 의미 |
| --- | --- |
| FLAX_PG_HOST | 정상 인증서 대상 이름, localhost |
| FLAX_PG_HOSTADDR | 실제 접속할 루프백 주소, 127.0.0.1 |
| FLAX_PG_PORT | 정상 TLS 및 평문을 제공하는 전용 서버 포트 |
| FLAX_PG_EXPIRED_PORT | 만료된 서버 인증서를 제공하는 포트 |
| FLAX_PG_PLAIN_PORT | TLS를 지원하지 않는 서버 포트 |
| FLAX_PG_USER, FLAX_PG_DATABASE | 제한된 검증 계정과 전용 DB 이름 |
| FLAX_PG_PASSWORD | 매 실행 새로 생성한 비밀번호, 출력 및 기록 금지 |
| FLAX_PG_CA, FLAX_PG_WRONG_CA | 정상 및 무관한 CA PEM 자료의 경로 |

Rust 검증은 CA 파일을 바이트로 읽은 뒤 메모리 PEM 파싱 결과로 신뢰 저장소를 만든다.
서버 이름과 실제 주소를 별도로 지정하여 잘못된 이름 시험이 DNS 실패로 끝나지 않게 한다.

DB 데이터는 검증용 테이블에서만 다룬다.
bytea는 바이트로, NUMERIC은 TEXT 매개변수에서 변환하고 TEXT로 읽어 비교한다.
u64 최댓값을 포함한 값은 십진 문자열로 전달한다.
문자열과 기본 정수도 별도로 왕복 비교한다.

#### 상태 변화

검증 실행은 준비, 서버 기동, 계정 및 DB 준비, 검사, 정리 순서다.
일부 서버만 기동된 실패도 기동한 서버를 모두 종료한다.
제품의 영속 상태나 기본 서버의 계정은 수정하지 않는다.
단계별 성공은 준비 완료와 소비 검증 통과를 구분한다.

#### 오류 및 예외 흐름

Cargo 또는 서버 준비 오류는 오류 코드와 비밀정보가 제거된 로그 위치로 반환한다.
인증 실패는 SQLSTATE 28P01을 확인하고,
TLS 실패는 정상 접속으로 동일 서버의 준비를 확인한 뒤 해당 실패 원인을 판정한다.
다른 네트워크 오류를 인증서 또는 인증 검증의 성공으로 취급하지 않는다.

TLS ON은 SslMode::Require와 명시적 ring ClientConfig를 사용한다.
실패 후 OFF로 재접속하는 코드를 두지 않는다.
SQL 오류가 난 트랜잭션은 rollback 또는 연결 폐기로 정리한 뒤 후속 질의를 확인한다.

### 선택한 설계와 판단 근거

#### 주요 설계 결정

- DB 전용 진입점은 `cargo-db`로 제공한다.
  기존 cargo의 필수 protoc 검사와 명령 해석을 유지하고 새 소비 모드를 명확히 구분한다.
- 새로운 직접 라이브러리도 Cargo 배포 소스를 원본으로 반입한다.
  기존 레지스트리 소스 규약과 체크섬 검사를 재사용한다.
- 준비 결과의 레지스트리 패키지 122개 중 기존 35개를 재사용하고 87개를 추가한다.
  구현 후 실제 검증 구성의 최종 잠금 파일과 목록을 다시 대조한다.
- getrandom의 0.4 및 0.2, wasi의 0.11 및 0.14,
  windows-sys의 0.61 및 0.52는 각각 계열 디렉토리에서 공존하게 한다.
  기존 파일의 내용은 유지하고 경로 및 레지스트리 목록만 함께 갱신한다.
  새 const-oid의 0.9와 0.10도 계열로 구분한다.
- libc 0.2.189, mio 1.2.3과 smallvec 1.16.1은 기존 버전을 재사용한다.
  준비 중 자동 선택된 새 호환 버전을 기존 소스의 교체 근거로 사용하지 않는다.
- DB 드라이버 및 PostgreSQL 표현 패키지는 data,
  TLS 연결은 networking, 일반 잠금, 풀과 암호 기반 패키지는 core를 기본으로 배치한다.
  개별 전이 패키지는 원본 설명의 주된 역할로 분류하고 근거를 목록에 보존한다.
- rustls는 Store별 ring 제공자를 전달한 builder를 사용하며 전역 기본 제공자를 설치하지 않는다.
- deadpool-postgres의 Manager와 Pool builder를 사용해 ON/OFF 풀을 독립적으로 구성한다.
  계정, 주소, 최대 연결 수와 대기 시간은 코드에서 명시적으로 전달한다.
- PostgreSQL 16 바이너리를 일반 사용자로 실행하는 독립 클러스터를 사용한다.
  관리자 권한은 OS 패키지 설치에만 필요하며 검증 실행에는 요구하지 않는다.

#### 선택 이유와 제약

기존 소스 및 실행기를 재사용하면 gRPC 소비자에게 새로운 명령이나 전역 설정을 요구하지 않는다.
별도 서버와 정상, 만료, 무관한 CA 자료는 요청된 성공 및 실패 조건을 재현 가능하게 만든다.
Cargo의 대상별 해결에 필요한 패키지도 공급하지만 Linux 외 대상의 실행 성공을 주장하지 않는다.

#### 검토한 대안과 선택의 영향

기존 cargo 명령의 protoc 검사를 일괄 제거하는 방법 대신 별도 모드를 선택했다.
기존 gRPC 준비 오류의 동작을 유지할 수 있다.
단일 TLS 서버를 검사 중 재설정하는 방법 대신 세 클러스터를 선택했다.
실패 조건을 독립된 포트로 구분하며 기존 연결 및 풀의 영향을 줄인다.
새 호환 전이 버전을 함께 공급하는 방법보다 기존 버전을 재사용해 불필요한 경로 공존을 피한다.

#### 넘겨받은 미결정 사항의 처리

Cargo 인터페이스는 공개 인터페이스에, 소스 배치와 버전 공존은 주요 설계 결정에,
서버 및 인증서 격리와 판정 기준은 동작 흐름 및 테스트 계획에 확정했다.
구현을 막는 설계 선택은 남지 않았으며 실제 결과는 구현과 검증 기록에 연결한다.

### 테스트 계획

#### 외부 의존성 격리 방법

DB는 별도 임시 클러스터, DB와 제한된 계정을 사용하고 모든 TCP 인증 규칙은 scram-sha-256으로 설정한다.
관리 준비의 로컬 Unix 소켓은 접근이 제한된 작업 디렉토리에서만 사용한다.
실제 Rust DB 검사는 루프백 TCP와 제한된 계정으로 실행한다.

인증서는 실행 시 OpenSSL로 생성한다.
유효한 CA와 서버 인증서, 같은 CA로 서명한 만료된 인증서 및 무관한 CA를 준비한다.
개인 키와 인증 정보의 파일 권한을 제한하고 Git에 포함하지 않는다.
비밀번호는 환경 또는 표준 입력으로 전달하며 명령 인자와 SQL 출력에 넣지 않는다.
서버의 문장 및 매개변수 기록을 제한하고 저장할 로그에서도 비밀정보를 제거한다.

#### 통합 테스트 적용 여부와 범위

Flax가 소스와 소비 연결을 책임지므로 checks/postgres-smoke에서
실제 드라이버, TLS 연결기, 풀과 PostgreSQL 16의 통합을 검사한다.
외부 소비 경로 검사는 저장소 밖의 공백 포함 경로와 독립 잠금 파일도 사용한다.
기존 checks/grpc-smoke는 기존 명령으로 실행한다.

#### E2E 테스트 적용 여부와 범위

Flax는 상위 제품 플랫폼이 아니라 소스 공급 프로젝트이므로 제품 E2E는 적용하지 않는다.
Rosemary의 Store 및 Track 동작은 두 요청서가 명시한 대상 범위 밖이다.
이번 실제 서버 검사는 Flax 소비 통합 검사로 구분한다.

#### 검증용 항목과 판정 기준

| 대상 | 확인 절차와 통과 기준 |
| --- | --- |
| Cargo 모드 | protoc 없는 임시 build-dir에서 cargo-db 설정 및 명령이 성공하고 PROTOC 강제 설정이 없음. 기존 cargo는 protoc 미준비 시 기존 오류를 유지 |
| 원본과 목록 | 원본 Git 트리, 모든 crate의 파일 목록 및 SHA-256 통과. 두 잠금 파일의 패키지에 대응하는 소스와 라이선스 기록 존재 |
| 오프라인 소비 | protoc 없는 새 build-dir 및 빈 전용 Cargo 캐시에서 --locked --offline 빌드 및 기본 검사 성공. 저장소 밖 독립 소비에서도 성공 |
| 인증 | TLS ON/OFF 질의 성공, 서버의 SCRAM 규칙과 검증 계정의 SCRAM 저장 형식 확인. 잘못된 비밀번호는 28P01로 거부 |
| TLS 정상 | 메모리 PEM CA와 정상 대상 이름 성공. TLS 1.2와 1.3으로 각각 접속하여 pg_stat_ssl의 실제 버전 확인 |
| TLS 실패 | 잘못된 CA 및 이름, 만료된 인증서와 TLS 미지원 서버에서 Require 연결이 실패하고 정상 연결의 준비 근거와 실패 원인을 대조. 자동 평문 재시도 없음 |
| 암호 제공자 | ring만 활성화하고 rustls-native-certs, webpki-roots, aws-lc-rs와 aws-lc-sys 없음. 명시적 ClientConfig 사용 전후 전역 기본 제공자 설치 없음 |
| 풀 | ON/OFF 풀을 함께 보유하고 각 연결의 pg_stat_ssl.ssl을 확인. 최대 2개를 보유하면 추가 획득이 설정된 wait timeout으로 실패하고 guard 반환 후 재획득 성공 |
| 트랜잭션 | commit한 행은 별도 연결에서 보이고 rollback한 행은 없음. SQL 오류 후 rollback 또는 연결 정리 뒤 후속 질의 성공 |
| 데이터 | bytea 바이트 일치, NUMERIC 소수와 u64 최댓값의 TEXT 왕복, 기본 문자열 및 정수 일치 |
| 보조 기능 | CA PEM 파싱과 알려진 SHA-256 입력 abc의 결과 일치. RwLock의 복수 읽기, 쓰기 배타성, 값 갱신과 guard 해제 후 재획득 성공 |
| 회귀와 정리 | 기존 gRPC smoke 및 관련 Python 검사 성공. 검증 후 전용 서버 종료와 비밀 시험 자료 정리 확인 |

Rust 기본 보조 검사는 lib 검사로, 실제 DB 검사는 별도 integration test로 둔다.
DB 검사는 필요한 환경이 없을 때 실패하며 ignore 또는 자동 skip으로 통과하지 않는다.
CLI 변경은 protoc 없는 모드와 기존 오류 동작의 실패 검사를 먼저 작성하여 TDD로 구현한다.
데이터 및 상태 검사는 실제 사용 동작을 판정하고 내부 함수와 같은 계산을 복제하지 않는다.

#### QA용 항목과 판정 기준

검증 로그, 최종 소스 및 기능 목록과 재현 명령을 사용자와 함께 검토한다.
두 요청서의 완료 조건에 대응하는 실제 결과와 미실행 범위를 확인한다.
설치 및 소비 가이드가 사용자가 실행할 수 있는 명령과 결과를 제공하는지 확인한다.
별도 제품 동작 검사나 전체 동시성 정확성 승인을 QA에 추가하지 않는다.

#### 테스트 실행에 필요한 환경과 준비 사항

설계 시점에 확인한 환경은 다음과 같다.

| 항목 | 확인 값 |
| --- | --- |
| OS/CPU | Ubuntu 24.04.4 / x86_64 |
| Rust/Cargo | 1.89.0 |
| Python | 3.12.3 |
| C 컴파일러 | GCC 13.3.0 |
| OpenSSL | 3.0.13 |
| PostgreSQL/psql | 16.15, Ubuntu 패키지 16.15-0ubuntu0.24.04.1 |

sudo에는 관리자 비밀번호가 필요해 사용자가 설치 안내의 apt 명령을 실행했다.
별도 클러스터에서 initdb, 서버 기동과 질의, SCRAM 저장 형식 및 ssl=on 설정을 확인하고 서버를 종료했다.
정상 및 만료 인증서와 무관한 CA를 생성해 정상 검증 및 만료 거부를 확인했다.
개인 키는 0600 권한으로 관리했고 출력 및 기록에 복사하지 않았다.

지정 버전과 검증 추가 기능의 임시 구성에서 `cargo check --all-targets --locked --offline`이 성공했다.
`cargo vendor --locked --offline`으로 registry 122개를 준비했고,
기존 35개의 체크섬 일치와 신규 87개의 라이선스 메타데이터를 확인했다.
이 결과는 준비용 캐시의 컴파일이며 완성된 Flax 소비 경로의 통과가 아니다.
샌드박스 안의 소켓 생성은 차단되어 허용된 외부 환경에서 서버 기동을 확인했다.
실제 DB 및 gRPC 검사에도 해당 소켓 권한이 필요하다.

준비 근거는 [컴파일 로그](../../../build/rosemary-preparation/compile-offline.log),
[해결 메타데이터](../../../build/rosemary-preparation/metadata-reused.json),
[vendor 로그](../../../build/rosemary-preparation/vendor.log)와
[PostgreSQL 준비 로그](../../../build/rosemary-preparation/postgres-readiness.log)다.
build 자료는 당시의 로컬 실행 근거이며 Git에서 제외된다.

최종 검사 구성은 [checks/postgres-smoke](../../../checks/postgres-smoke/Cargo.toml),
최종 활성 기능은 [Linux 기능 목록](../../../checks/postgres-smoke/features-linux.json),
기능 합침의 해석은 [소비 안내](../../../docs/rosemary-integration.md#공급-버전과-기능)를 따른다.
준비 단계의 기능 요약을 최종 기능의 정본으로 사용하지 않는다.

분할하지 않는다.

1. DB 모드 및 기존 Cargo 동작의 실패 검사를 작성하고 실행기를 수정한다.
2. 준비한 원본을 반입하고 필요한 기존 계열 경로 및 목록을 갱신하여 무결성을 확인한다.
3. Rust 보조 검사, 잠금 파일과 실제 DB 검증 실행기를 작성한다.
4. 새로운 출력 경로에서 오프라인 소비와 실제 DB 및 기존 회귀를 실행한다.
5. 기능, 결과와 재현 문서를 연결하고 구현 결과를 사용자 확인 대상으로 제출한다.

모든 DB 계정 비밀번호와 개인 키는 실행 자료에만 두며 저장소와 보고에 복사하지 않는다.
